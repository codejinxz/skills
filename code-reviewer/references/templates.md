# 评审模板：派发指令 / 子报告 / 全局汇总

> 模板中 `<>` 为填入位，由主会话按目标项目实际信息填写；派发指令必须逐段填完后再发给子代理。

## 一、子代理派发指令模板（自包含）

```markdown
## 角色

你是 `<项目名>` 代码评审专员，负责聚簇 `<聚簇名>` 的 `<N>` 个维度评审。（按模块拆时本行写"负责模块 `<模块名>` 的全部 32 维评审"，N=32。）

## 评审范围

- 代码根目录：`<绝对路径>`
- 本轮范围：`<模块/包/全库，含排除目录>`
- 技术栈：`<语言、框架、构建工具、ORM、存储>`

## 项目契约要点（评审硬性基准）

<从 AGENTS.md / CLAUDE.md / CONTRIBUTING.md 摘录的硬性条款，逐条列出；
无成文契约时写"该项目无成文契约，按下方通用检查点评审">

## 所辖维度与检查点

<从 references/dimensions.md 摘录本聚簇全部维度及检查点原文>（按模块拆时摘录全部 6 聚簇原文）

## 已知缺口（不重复报告）

<已知缺口/存量限制清单及编号；与这些重叠的发现只在报告中标注编号，不计入统计>

## 铁律

- **只读**：不得修改上述代码范围内的任何文件；只把报告写入 `<输出目录>/<NN-主题>.md`。
- **证据强制，且证据不可得 ≠ 未发现**：每条计入统计的发现必须给 `文件路径:行号` + 关键代码片段；定位不到证据的放「待核实」区，不计入统计。逐维结论四态：**有发现 / 未发现 / 不适用+依据 / 证据不可得+缺什么**——「不适用」只有两种合法依据（项目形态不适用、无评测对象），无依据视为未覆盖；需要外部数据才能评的子项标「证据不可得」并写明缺什么、需要什么才能确认，进「待核实」区——不得写成"未发现"或"无风险"；能本地评的子项照常评。四态按子项标注、可组合；**多态并存时按 有发现 > 不适用 > 证据不可得 > 未发现 取主结论**，子项级差异在自查表结论单元格内并列标注（如"有发现；CVE 子项证据不可得"）。
- **四级定级**：P0 阻断、P1 严重（主链路缺陷、明确 bug，及违反上述契约要点的最低档）、P2 一般（确定性改进项）、P3 建议（风格与优化）。**违反契约硬性条款最低 P1，触及安全或数据完整性升 P0；P0 封顶，不再有"高一档"。** **P0 典型锚点**（从宽认定）：硬编码生产密钥/数据库凭据入库、注入可利用、越权可达（水平/垂直/IDOR）、数据丢失或损坏路径、敏感信息明文进日志或响应。**契约文档自身失同步**（描述与实际不符）→ 至少 P2，并标注"该条款影响基准可靠性"；文档旧、代码新时不得判代码违规。
- 不虚报、不凑数；零发现的维度如实写"未发现"。
- **覆盖深度如实标注**：无法在合理成本内审完所辖范围时，优先深审高风险区，并在报告头部如实标注快扫范围，禁止把快扫包装成全量。

## 报告模板

<嵌入下方「子报告模板」，含文件名>

## 完成标准

- 所辖 `<N>` 个维度每个都有结论（含"未发现"）。
- 全部计入统计的发现证据可定位。
- 覆盖深度已在报告头部如实标注（全量深审 / 高风险深审 + 快扫范围）。
- 报告已写入指定路径并通过自查。
```

## 二、子报告模板

```markdown

- **评审范围**：<模块/全库路径>
- **执行形态**：<多代理 / 单会话亲审（降级原因：<...>）>
- **覆盖深度**：全量深审 / 高风险深审 + 快扫（快扫范围：<...>）
- **所辖维度**：<维度编号与名称列表>
- **评审方法**：<静态阅读 + 对照契约/文档，跑了哪些只读命令>
- **统计**：P0 <n> · P1 <n> · P2 <n> · P3 <n> · 待核实 <n> **条**（条目数） · 证据不可得 **维度级 <n> 维 · 子项级 <n> 项**（列于自查表与待核实区，不计入"未发现"；整维与部分子项分开计，与汇总的"证据不可得维度数"对应）。**量纲规则：每个证据不可得的维度/子项在待核实区至少一条对应记录；待核实条目数可以多于证据不可得项数**

## 发现列表

### <编号> [P<级别>] <维度名>：<一句话标题>

- **位置**：`<文件路径:行号>`
- **问题**：<具体描述，为什么是问题>
- **证据**：

```text

```

- **修复建议**：<具体可执行的建议>
- **影响面**：<波及的调用方/数据/下游，或"仅局部">

（逐条重复以上结构）

## 待核实区

<有怀疑但无证据定位的项，**以及需要外部数据才能确认的项**（如"CVE 完整比对——需要 NVD/OSV 查询"）；每条写明**需要什么才能确认**；不计入统计，也不得计为"未发现">

## 与已知缺口的重叠

<仅标注编号，如"与 GAP-ANALYSIS §x 重叠，不重复报告">

## 维度覆盖自查表

|---|---|---|
| <逐维度一行> | <有发现 / 未发现 / 不适用+依据 / 证据不可得+缺什么；**可组合**：同维本地有发现、个别子项需外部数据或形态不适当时并列标注> | <n> |

## 结尾建议（如触发，未触发删除本节）

## 三、汇总报告模板（00-评审汇总.md）

```markdown
# 代码评审全局汇总

- **评审日期**：<日期>
- **目标与范围**：<项目、范围、排除项>
- **子项目规模拆行**：<多子项目仓库时按子项目列栈/文件数/LOC/高风险区；单项目写"单项目">
- **副本清单与权威判定**：<重复副本仓库时列副本路径、权威判定依据、副本漂移发现编号；无副本则写"无">
- **执行形态与确认留痕**：<多代理 / 单会话执行（降级原因：<...>）/ 预授权离线（默认排除项陈述：<...>）+ 子报告提出的转用建议在此汇列（如"03 报告建议转用 test-engineer 做测试深审"）>
- **拆分方案**：<子代理清单及其所辖聚簇/维度，附一句话理由，并标注该代理的深审/快扫范围>
- **基准说明**：<依据的契约文件；无契约时注明按通用标准>

## 总体统计

| 级别 | 数量 | 占比 |
|---|---|---|

**证据不可得维度数**：<n> 维（<列出；因外部数据缺失或评审降级而无法给结论的维度，防止误读为"全审无问题"）

## 维度 → 子报告映射表

**须 32 行逐行填写，缺行即视为汇总不合格；填完做恒等式校验。**

| 聚簇 | 维度 | 子报告 | 结论 | 发现数 |
|---|---|---|---|---|

（32 个维度逐行，结论列填**维度主结论**（判定优先级最高类：有发现 > 不适用 > 证据不可得 > 未发现）：有发现 / 未发现 / 不适用+依据 / 证据不可得+原因——降级"未覆盖"写"证据不可得（评审降级未审）"。**按模块拆分时每个维度按模块分行**（如"维度 8 · server"、"维度 8 · web"），结论列写该模块的结论，发现数汇总；恒等式仍按 32 维合并后的主结论校验。**恒等式校验：32 = 有发现 <n> + 未发现 <n> + 不适用 <n> + 证据不可得 <n>**，按主结论计、对不上即汇总不合格；子项级证据不可得与 FZ 副本漂移发现均不进恒等式，分别体现在"覆盖深度与未覆盖说明"和「副本漂移发现」节。）

## Top 10 优先级问题

排序规则：**先按 P 级；同级内按影响面广度（跨模块/跨系统 > 单模块 > 局部）；同广度内按修复成本从低到高**。

<从全部子报告中合并去重后排序，每条注明来源子报告与编号。**若存在证据不可得的关键维度，本排序基于不完整信息，可能失真——在此注明**（如"维度 9 CVE 比对证据不可得，供应链相关排序可能低估风险，详见覆盖说明"）>

## 覆盖深度与未覆盖说明

<深审 / 快扫 / 降级亲审 / 失败未覆盖，逐项如实交代；交叉深审模式下逐维度列明覆盖深度；子代理失败降级的簇在此标注「覆盖不完整」并列出缺失维度清单；**「证据不可得」的维度在此单列并分列两种原因**——① **资产缺失失效**（项目缺外部数据，如"9 CVE 完整比对——需外部漏洞库"）、② **评审降级未审**（子代理失败且未亲审）——与"未发现"明确区分>

## 跨维度共性问题

<多个子报告重复出现的模式，如"多处吞异常""多模块越权路径"，指出系统性根因>

## 整改路线

- **合入前必须修**：<P0 全部 + 高影响 P1>
- **本迭代修**：<余下 P1 + 低成本 P2>
- **后续排期**：<余下 P2 + P3>
