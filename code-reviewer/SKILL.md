# 多代理全维度代码评审

## 概述

以"主会话当评审负责人 + 多个只读子代理并行评审"的架构，对目标代码做 32 维度、不重不漏、证据强制的系统评审。主会话不逐行评审全部代码，但对拆分方案、子报告质量与维度完整覆盖负责。**本 skill 只审不改，流程内不存在修复环节**；用户要求修复时，以汇总的「合入前必须修」清单为输入另行发起任务，不并入本流程。

## 触发参数盘点

每次评审开始前，从调用消息与项目文件中盘点以下参数；**只对缺口追问，信息足够立即开工**。缺省值仅在与用户确认过关键项后使用。

| 参数 | 说明 | 默认值 |
|---|---|---|
| 目标代码范围 | 全库 / 某模块 / 某语言目录（如 `server/`） | 当前工作区的主体代码目录 |
| 报告输出目录 | 所有报告唯一落盘位置 | 工作区外或用户指定目录；不存在则创建，写入受限时向用户报告而不是改投别处 |
| 评审基线 | 项目契约与需求文档 | 按「评审基准自动发现」探测 |
| 已知缺口 | 不重复报告的存量登记 | 按「评审基准自动发现」探测 |
| 排除范围 | 明确不审的目录 | 生成物、第三方库、原型目录、docs 文档本身；**默认排除项必须随拆分方案简报一并列给用户确认，不得静默执行**；探测到例外（vendor 内定制补丁、原型已成线上依赖）时单独提示 |

## 评审基准自动发现（通用化关键）

评审必须以**目标项目自己的规则**为基准，禁止把某个项目的约定强加给另一个项目。逐项探测，找到什么用什么：

1. **契约文件**（决定"违反项目规则"的定级依据）：`AGENTS.md`、`CLAUDE.md`、`.cursor/rules/`、`CONTRIBUTING.md`、`README.md`、`.editorconfig`、lint 配置。找到的硬性条款（分层依赖、禁止事项、命名规范、DoD）视为评审基准，违反者按铁律 3 定级（最低 P1，触及安全或数据完整性升 P0）。
2. **需求与接口契约**（决定"功能/需求覆盖/缺失项"的对照源）：`docs/` 下的 PRD、API 文档、DATA-MODEL、设计决策文档。
3. **已知缺口登记**（决定"不重复报告"清单）：`CHANGELOG.md`、`GAP-ANALYSIS.md`、TODO/FIXME 集中登记、issue 索引。子报告中与已知缺口重叠的发现仅标注编号，不计入统计。
4. **以上均不存在时**：以 `references/dimensions.md` 的通用工程检查点兜底，且**不得虚构项目规则**；报告中注明"该项目无成文契约，按通用工程标准评审"。

## 评审铁律

1. **只审不改**：主会话与全部子代理不得修改目标仓库任何文件；所有产出只写入报告输出目录。
2. **证据强制，且证据不可得 ≠ 未发现**：每条计入统计的发现必须给出 `文件路径:行号` + 关键代码片段；定位不到证据的猜测一律放报告末尾「待核实」区，不计入统计。**需要外部数据才能评的子项**（供应链 CVE 比对、CI 平台运行历史、issue 系统关联等本地拿不到的）：按「**证据不可得**」在维度自查表单列，写明**缺什么、需要什么才能确认**，进「待核实」区——它既不是"未发现"（没查到问题），更不得写成"无风险"；无外部数据的维度不得因拿不到外部证据而整维免审，能本地评的子项照常评。
3. **四级定级**：P0 阻断、P1 严重（主链路缺陷、明确 bug，及违反契约硬性条款的最低档）、P2 一般（确定性改进项）、P3 建议（风格与优化）。**违反项目契约硬性条款的问题最低 P1，同时触及安全或数据完整性时升为 P0；P0 为封顶级别，不再有"高一档"。** 无契约项目按维度检查点的严重性定级。**P0 典型锚点**（从宽认定，触线即 P0）：硬编码生产密钥/数据库凭据入库、注入可利用（SQL/命令/反序列化）、越权可达（水平/垂直/IDOR）、数据丢失或损坏路径（无回滚的破坏性操作）、敏感信息（密码/token/完整 PII）明文进日志或响应。**契约文档自身失同步**（描述与实际不符，非代码违反契约）→ 至少 P2，且须在报告中标注"该条款影响基准可靠性"——文档旧、代码新时不得判代码违规；发现文档错了必须报，不得静默。
4. **不重不漏可追溯，恒等式闭合**：32 个维度每个都归属某份子报告，汇总中给出"维度 → 子报告"映射表（含结论列）。**恒等式：32 = 有发现 + 未发现 + 不适用 + 证据不可得**（降级"未覆盖"归证据不可得、原因是"评审降级未审"）；映射表 32 行填完后逐类合计校验，缺类、多类或对不上即汇总不合格——防"看起来全审了，实际没全审"。**恒等式按维度主结论计**（取判定优先级最高的那一类：有发现 > 不适用 > 证据不可得 > 未发现）；**子项级的"证据不可得"只进子报告统计行与待核实区，不进 32 维恒等式**——混合维（如"本地有发现 + CVE 子项证据不可得"）在映射表结论列填主结论"有发现"，子项缺证据在「覆盖深度与未覆盖说明」以"维度 9（部分子项：CVE 未比对）"形式体现，不丢信息也不重复计账。**FZ 副本漂移发现同样不进恒等式与映射表**（记账边界见第 1 步副本仓库规则：只进「副本漂移发现」节、总体统计与 Top 排序）。
5. **子代理指令自包含**：子代理看不到主会话上下文，派发指令必须包含它所需的全部信息（见 `references/templates.md` 派发模板），包括从契约文件摘录的关键条款要点。
6. **不虚报**：子代理不得为了凑数降级或夸大问题；数量不代表质量，零发现的维度如实写"未发现"。

## 工作流程

### 第 1 步：摸底

- 读契约文件与需求文档，摘录硬性条款形成「契约要点清单」。
- 列出目标范围的模块/包清单与规模（文件数、行数），识别高风险区：鉴权、事务、并发、外部 IO、金钱/数据完整性、幂等、缓存。
- 探测已知缺口登记，形成「不重复报告」清单。
- **多子项目仓库（monorepo：1 后端 + N 前端等）**：规模统计与拆分方案**按子项目拆行**，不合并成一行——各子项目的栈、规模、高风险区不同，混在一起会让拆分方案失真；拆分时优先按子项目划子代理边界。
- **重复副本仓库**（同一代码库存在多份拷贝，如 `proj/` 与 `proj-backup/`、`proj-final/`）：先判定**权威副本**（有 git 历史且最新的为权威；均无版本控制时以最近修改时间为准并注明依据），**只对权威副本计账评审**；其余副本仅做两件事——① 与权威副本的漂移对比（副本里有而权威里没有的改动，构成「副本漂移」发现，P2 起评：副本被误当权威使用即是风险），**编号用 `FZ-<序号>`，由主会话亲审产出，写入 `00-评审汇总.md` 的「副本漂移发现」节并计入总体统计与 Top 排序**；② 在汇总中列明副本清单与判定依据。**FZ 发现的记账边界：不归属任何 32 维，不计入恒等式，不进「维度 → 子报告映射表」——它单独列在「副本漂移发现」节，其 P 级计入「总体统计」的级别计数并在 Top 排序中参与排序；恒等式校验只针对 32 维，与 FZ 发现数量无关。禁止把 FZ 硬塞进某个维度（如 15 技术债、32 缺失项）造成统计污染。**禁止把每个副本当独立项目各评一遍。

### 第 2 步：设计拆分方案

由主会话根据代码规模与结构决定拆分方式，先向用户简报方案与理由（含默认排除项确认）再派发。**用户不在线时（预授权离线形态，如由子代理全程执行、用户已预先确认范围）**：确认问句改为陈述（"默认排除项为 <...>，如需调整请告知"）写入汇总头部，不阻塞流程；但**排除范围与拆分方案必须在 `00-评审汇总.md` 的「拆分方案」节完整留痕**——离线不等于免确认，是确认后置。

**规模决策树**（按目标范围源码文件数量选起点）：

- **< 200 个源码文件**：1–2 个子代理（聚簇合并），每个子代理可通读全库，避免多代理重复通读的浪费。
- **200–2000 个**：维度聚簇或按模块拆，4–8 个子代理；模块边界清晰者优先按模块拆。
- **> 2000 个**：交叉深审——高风险模块（鉴权、事务、并发、外部 IO、金钱/数据完整性）全维度深审，其余维度快扫。

文件数仅为粗代理：一文件一类的语言（Java）与脚本型语言（Python/JS）单文件体量可差一个数量级，单文件平均行数明显偏离常规时按**总 LOC 折算校准档位**（经验值：总 LOC 超 10 万视同 > 2000 档）。

任何包含快扫的方案，必须在拆分方案与最终汇总中**逐维度标注覆盖深度（深审/快扫）**，禁止把快扫包装成全量评审。三种拆分模式按需选用或混搭：

- **维度聚簇**：把 32 个维度按 `references/dimensions.md` 的 6 个聚簇（或自行聚簇）分给若干子代理，每个扫全量代码但只审自己那组维度。适合中小型代码库，报告主题聚焦。
- **按模块拆**：按业务模块分给子代理，每个审全部维度。适合模块边界清晰的大型代码库，注意每份报告的维度覆盖都要求 32 维不缺。
- **交叉深审**：高风险模块 × 相关维度深审，其余维度快扫。适合时间或预算受限时，快扫部分在汇总中如实标注覆盖深度。

派发原则：每个子代理职责聚焦、彼此可并行、总规模 4–8 个子代理为宜（小库按决策树缩减）；单个体积过大时宁可多拆；预算或时间受限时，**主动缩小范围并如实标注，而不是降低证据标准**。

**子代理失败处理（不得静默吞掉）**：子代理超时、报错或返回残缺报告时——先重试一次；仍失败则主会话降级亲审，亲审顺序按 `references/dimensions.md` 各聚簇标注的「降级优先级」执行，并在拆分方案与汇总中把该簇标注为「覆盖不完整」并列出缺失维度清单。任何情况下不允许"32 维全覆盖"的承诺因失败而静默打折。

**整个子代理机制不可用时（整体降级，与单个失败不同）**：执行环境不支持子代理（工具不存在）、或**连续两次派发失败/被终止**、或并发能力受限到只剩主会话时——不要逐簇重试硬撑，改为**主会话单会话亲审**：串行执行全部聚簇、同样满足维度闭环与证据要求、汇总头部标注「单会话执行（降级原因：<...>）」并告知用户，但不中断流程。派发模板此时直接当亲审清单用（其中"角色"等代理专属措辞按亲审语境改读，重试类代理专属条目跳过），不需要改写。预算或时间撑不住全量亲审时，按规模决策树降档（如 2000+ 档改按交叉深审）并如实标注覆盖深度——**降档是允许的，静默打折不允许**。

### 第 3 步：并发派发

- 用子代理工具并发拉起评审子代理（run_in_background 并行）；**同时运行的子代理不超过 6 个，超出排队等待**；子代理使用只读权限或在其指令中明确禁止写入。
- 每个派发指令按 `references/templates.md` 的「子代理派发指令模板」组装：目标范围、所辖维度（从 `references/dimensions.md` 摘录对应检查点）、契约要点、已知缺口清单、报告模板、输出路径、完成标准。
- 子报告文件名由主会话统一编排（如 `01-正确性与可靠性.md`），汇总固定命名 `00-评审汇总.md`。

### 第 4 步：回收质检

- 逐份核对：所辖维度是否全部有结论、计入统计的发现是否证据齐全、是否误报已知缺口。
- **真实性抽验**：对每份子报告，从其 P0/P1 发现中随机抽取 `min(5, 该报告 P0/P1 总数)` 条，不足 5 条则**全部核验**；回源码核实行号与代码片段是否真实存在。抽验不符项所在子报告**整体退回重审**——抽到编造就意味着该子代理其他发现同样不可信，不得只修正抽中条目；退回时要求该子代理对**全部 P0/P1 逐条附源码上下文自证证据**，而非重扫全量。
- 不合格的退回对应子代理补审（续用原代理或重发指令），直到全部达标。

### 第 5 步：全局汇总

主会话亲自编写 `00-评审汇总.md`，按 `references/templates.md` 的「汇总报告模板」，包含：维度→子报告映射、跨报告去重、按级别统计、Top 10 优先级排序、跨维度共性问题、按「合入前必须修 / 本迭代修 / 后续排期」的整改路线、总体结论。

## 完成标准（Done when）

- 报告输出目录下存在全部子报告 + `00-评审汇总.md`，目录清单与拆分方案一一对应。
- 32 个维度全部被覆盖且在汇总中可追溯；每条计入统计的发现证据可定位，无证据项全部在「待核实」区；快扫或降级覆盖在汇总中逐维度如实标注。
- P0/P1 真实性抽验全部通过。
- `git status`（或等效手段）确认目标仓库无任何改动。
- 最终回复包含：各级别问题数量、Top 5 风险摘要（摘自汇总的 Top 10，可按回复场景精选）、报告文件清单；并询问是否需要把「合入前必须修」的问题登记进项目的待办文档（此动作需另行确认，本次不做）。**预授权离线形态下**该问句改为陈述（"如需登记请告知，本次未做"），不阻塞。

## 资源

- `references/dimensions.md` —— 32 个评审维度的 6 大聚簇与每维度通用检查点。派发子代理时读取对应聚簇，摘录进自包含指令。
- `references/templates.md` —— 子代理派发指令模板、子报告模板、汇总报告模板，直接套用后填入项目实际信息。
