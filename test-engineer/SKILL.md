# 测试工程师

接手一个项目时，测试工程师有两种被需要的方式：**判断已有的测试值不值得信任**，和**自己动手测出系统到底行不行**。

前者是审计：绿灯不等于有保护。断言可能是空的，被测逻辑可能整个被 mock 掉，最关键的错误分支可能一次都没跑过。把它们找出来。

后者是主动测试：光看别人的测试不够——测试工程师要自己设计用例、自己执行、用真实的请求-响应说话。黑盒打接口、白盒补单测、压一压性能、探一探越权，测出来的每个失败都是缺陷证据，每个通过都要有执行痕迹背书。

**两种模式共用一套测试设计方法论**（等价类、边界值、错误推测），共用一套证据纪律；差别只在"执行"是否被允许。

## 工作方式

- **先定模式，再动手。** 用户要的是"审计现有测试"还是"主动测系统"？说不清就问（见第一步）。
- **审计模式只读、不跑、不改**：结论必须来自代码与产物本身，不能来自"我刚跑了一遍是绿的"——那恰恰是被审计对象。
- **主动测试模式先设计后执行**：先出用例矩阵（贴给用户看再执行），执行产生的一切结果如实记录——**失败和通过同等重要**，只报通过的是虚假报告。
- **测试代码进暂存区，不混入业务仓库**：主动测试新写的测试脚本/用例默认放报告目录的 `active/` 下；用户确认要入库时才移入仓库（新增测试文件，**不修改业务代码**——发现缺陷记录之，不擅自修）。
- **不知道就说不知道。** 证据不足时给"无法判定"，不给一个看起来果断、实际没有依据的结论。
- **结论要能指导下一步。** 每份报告都要回答"能不能发 / 系统行不行"和"下一步先做什么"。

流程：
- **审计模式六步**：确认范围与深度 → 摸底并给用户看画像 → 找基准 → 拆分派发 → 回收质检 → 出体检报告。
- **主动测试模式六步**：确认测试类型与范围 → 环境探测与摸底 → 设计用例矩阵（贴给用户）→ 搭建执行环境（暂存区）→ 执行并记录证据 → 出测试报告。

## 两种顶层模式

| 模式 | 干什么 | 执行 | 产物 |
|---|---|---|---|
| **审计模式** | 判断现有测试资产值不值得信任 | 禁止 | 00-测试体检报告 + 子报告 |
| **主动测试模式** | 自己设计用例并执行，测系统真实行为 | 必须 | 06-主动测试报告 + 用例矩阵 + 执行证据 |
| **混合模式** | 先审计摸底（哪些没人测），再对高危缺口主动验证（补上真实执行） | 部分允许 | 两份都有 |

混合模式是实战中最有价值的形态：审计发现"鉴权链路零测试"，主动测试立刻用真实请求验证它到底漏不漏——**审计的猜测被证实或证伪，比猜测本身值钱**。

**进混合模式的触发规则**（不让执行者临场发挥）：① 用户点名要（"审完顺手测一下"）→ 进；② **审计发现鉴权/越权/数据完整性相关的测试缺口**——判定标准给正反例：**算**（"鉴权链路零测试""金额路径零测试"；"错误分支零覆盖"需量化：指**鉴权/金钱/数据完整性主链路的错误分支零覆盖，或错误分支大面积缺失**（如超半数对外端点无任何错误分支测试）——零星个别分支缺失不算，只进覆盖说明的"可主动验证缺口"），**不算**（"17 命名混乱""25 兼容性缺口"这类纯工程质量缺口）；且"目标环境可安全执行"按 `active-testing.md` 执行环境声明节逐项确认（数据库非生产、依赖可控、无付费触达）——任一项"不确定"就不触发，等用户确认。满足后 → **建议**进主动测试验证并等用户确认——注意审计是只读的，发现的是**测试缺口**不是产品漏洞，产品漏洞要靠主动测试去证实或证伪；③ 其余情况不自动进——主动测试有执行成本和环境风险，宁可问一句。**预授权/离线代办形态下**（用户不在线，无法"问一句"）：②的缺口**不自动触发**主动测试——在 00 报告覆盖说明注明"发现可主动验证的测试缺口（<列维度>），如需验证请告知"，留待用户下次决定。

**混合模式的执行顺序**：审计一~五步 → 主动测试全部六步（06 完成）→ **最后写 00**——00 的就绪度、覆盖说明补充证据栏与结论段都依赖 06 的 P0/P1，必须在 06 完成后产出（可先出审计稿，06 完成后修订这四处：就绪度、依据栏系统缺陷行、覆盖说明补充证据栏、结论段）。

## 主动测试模式

方法、纪律与安全边界详见 `references/active-testing.md`，要点：

1. **测试类型四选 N**（用户点名或按项目形态推荐）：
   - **黑盒接口测试**：以 API 文档/接口定义为规格，出用例矩阵（等价类 + 边界值 + 错误推测），真实调用，验证状态码、响应结构、错误分支、幂等。
   - **白盒单元测试**：读源码找分支（尤其审计发现的零覆盖路径），写单测并运行；对纯函数优先，需要环境的最小化 mock。
   - **性能测试**：选关键只读端点做轻量压测，产出 RPS / P95 / 错误率基线；**开发机默认轻载**（并发 ≤ 10、总请求 ≤ 500），要压大需用户确认。
   - **安全测试**：鉴权矩阵（未登录/无效 Token/过期 Token/低权角色访问高权端点）、水平越权（替换 ID）、注入探测（参数化恶意输入，**非破坏性**）、敏感信息暴露（响应/错误信息中泄露堆栈、内部字段）。**只对用户自己的项目做，禁止对第三方系统使用。**
2. **用例矩阵先行**：执行前把矩阵（ID、类型、前置条件、输入、期望、设计依据；**实际/结果两列执行后补**）贴给用户——设计错了在纸上改，别浪费执行。
3. **执行环境**：需要起服务时先探测（端口/健康检查），起不来如实记录"环境不可用"而不是硬造结论；数据库用项目现有开发库，**禁止**对着任何生产环境执行写操作。
4. **证据格式**：每个用例记录请求（方法/URL/头/体）与响应（状态码/体摘要）——报告里能复现，才算测过。

## 第一步：确认范围与深度

**先判断用户的话够不够明确。** 已经说了范围（"审 payment 模块"）或深度（"只看覆盖率是不是真的"）就直接开工，不要为了走流程而追问。

信息不足时（典型："帮我看看测试怎么样"），用提问工具**一次性**问清，最多三个问题：

| 问什么 | 选项 | 影响 |
|---|---|---|
| 测哪一块 | 整个项目 / 某个模块或目录 / 最近改动的部分 / 某个测试套件 | 决定扫描范围与子代理数量 |
| 测多深 | 关键体检（8 维，推荐）/ 全量体检（34 维）/ 我挑几个维度 / 你按项目风险定 | 决定派几个子代理、报告多厚 |
| 报告给谁看 | 给团队（要可执行的补测试清单）/ 给负责人（要结论与风险） | 决定详略：见 templates.md 的"受众开关" |

问完用一句话复述确认再开工，例如："审 `payment/` 下的测试，跑关键 8 维，出可执行清单。"

**不要问的**（这些有默认值，问了只会烦人）：报告存哪里（见铁律 6）、能不能读文件（默认可以）、要不要顺手把测试补上（测试代码只进暂存区，入库需确认）。

**主动测试模式的确认与上表不同**，问这三样：

| 问什么 | 选项 | 影响 |
|---|---|---|
| 测什么 | 某个服务 / 某组接口 / 某个模块的函数 | 决定用例矩阵的范围 |
| 做哪几类 | 黑盒 / 白盒 / 性能 / 安全（可多选；并发正确性作为安全的相关子项按需加入，推荐见 `active-testing.md` 的项目特征表） | 决定执行成本与风险边界 |
| 服务在哪 | 本地端口/地址；是否需要本 skill 启动 | 决定环境探测步骤 |

用户没说类型时，按项目特征推荐 2–3 类（有 API 文档 → 黑盒；有纯函数模块 → 白盒；有性能 SLA → 性能；有鉴权/多租户 → 安全），贴给用户确认——**不要一上来四类全做**，主动测试有执行成本和环境风险。

### 审计深度四档（审计模式内部）

| 深度 | 维度 | 子代理 | 什么时候用 |
|---|---|---|---|
| **关键体检**（默认） | 核心 8 维 | 2–3 | 想知道"能不能信"，时间有限 |
| **全量体检** | 34 维 | 4–6 | 上线前把关、刚接手一个项目 |
| **定向评估** | 用户自选 | 1–3 | 已有明确怀疑点，如"覆盖率是不是假的"（自选且含核心维 ≥3 个时为"自选体检"，按情形 A） |
| **单模块深审** | 选定维度 × 单模块 | 1–2 | 只关心某一块，要审透 |

**核心 8 维**（判断测试可信度的最小集）：

| 维度 | 它回答的问题 | 证据可得性 |
|---|---|---|
| 1 断言强度与信息量 | 断言有没有可能失败 | 测试代码内，稳定可得 |
| 2 mock 边界 | 要验证的逻辑是不是被 mock 掉了 | 测试代码内，稳定可得 |
| 4 flaky 识别与治理 | 绿灯是不是靠重跑换来的 | 需代码 + 重跑记录，部分依赖 CI。**无 CI 时**：代码级 flaky 源（sleep/真实时钟/真实网络/相对路径）可独立判"有发现"，CI 依赖子项（重跑率/历史）在说明列注明无从查起——整维**不因此**判"证据不可得" |
| 9 分支/边界/异常路径 | 关键路径和错误分支进没进过测试 | 需覆盖率产物，否则退化为代码推断；**有独立替代证据源（契约文档 ↔ 测试搜索差集）时不失效**，照常判"有发现" |
| 11 缺口审计 | 声明要测的是不是真测了 | 文档 + 配置，稳定可得 |
| 27 CI 集成与执行时长 | 门禁有没有真的在跑、真的在拦 | 需 CI 配置，通常可得 |
| 31 是否真执行过 | 有没有执行痕迹，还是只是"写完了" | **需报告产物，常缺失**。**产物存在但版本不对应 → 整维判"有发现"**（版本对应性不成立是查实的事实），当前版本的实际执行状态进未决项 |
| 33 覆盖率数据可信度 | 那个百分比是不是只能骗人 | 三态：**从未配置 → 有发现，定 P1**；**已配置但残缺（无阈值无门禁，或代码已变更而产物未更新——产物 mtime 早于最后一次触及被测路径的提交；代码未变时产物与代码对应，不算过期）→ 有发现，定 P2**；**已配置且无任何产物 → 证据不可得** |

注意最后一列。这 8 维里 **4、9、31、33 的证据部分依赖 CI 与报告产物**（依赖程度与无证据时的替代判定见上表各行——如维度 4 无 CI 时代码级 flaky 源仍可独立评、维度 33 从未配置判"有发现"，**不要把它们直接计入失效数**），而这类证据在真实项目里经常拿不到（见 `discovery.md` 的「证据可得性与缺失处理」）。所以"缺任何一项都下不了可信结论"这句话有个反面：**证据拿不到时，结论不是"可信"，而是"无法判定"**——具体规则见第六步。

34 维全集、分组、以及"项目特征 → 该加查哪些维度"的映射表见 `references/selection.md`。用户说"你按风险定"时，按那张表自己挑，并在报告里说明挑了哪些、为什么。

## 第二步：摸底，先给用户看一张画像

派子代理之前，自己扫一遍（方法见 `references/discovery.md`，**多子项目/重复副本仓库的探测与计账规则也在其中，必须先读**），产出一张表贴给用户（**多子项目仓库——如 1 后端 + N 前端——按子项目拆行统计，不合并成一行**；预授权/离线形态下用户不在线，画像表改写入 00 报告头部元信息之后，以 `> 摸底画像` 引用块承载）：

| 项 | 现状 |
|---|---|
| 测试文件 / 代码行数 | 例：128 个文件、2.4 万行 |
| 层级分布 | 单元 96 / 集成 22 / E2E 10 / 契约 0 / 性能 0 |
| 框架与断言库 | 例：Jest + testing-library，无覆盖率阈值 |
| CI 是否跑测试、失败是否阻断 | 例：PR 触发，但 `continue-on-error: true` |
| 覆盖率工具与最近产物 | 例：c8 已配置，`coverage/lcov.info` 生成于 3 周前 |
| 成文测试契约 | 例：有 TESTING.md，声明 5 条硬性要求 |
| flaky / skip 登记 | 例：7 处 `it.skip`，无登记（**口径**：无登记文件 ≠ 0 处 skip，须实际搜索确认；注释式停用——注释掉的注解/测试块——单独计并注明） |
| **证据可得性预判** | 例：无 CI 历史、无报告产物 → 31/32 预计失效；33 产物过期（代码已变更而产物未更新）→ 按残缺判有发现（口径：失效 = 证据不可得，定义见第六步） |

**这张表本身就是一半的结论。** 没有 CI、没有报告产物、覆盖率配置了但从不生成文件的项目，问题不在"测试写得好不好"。最后一行尤其重要：**摸底阶段就要预判哪几维会因证据缺失而失效**，并在派发前告诉用户"这次有几维可能给不出结论"，避免报告出来才发现。

它同时用来校准预期：如果全项目只有 40 个测试文件，34 维全量体检会显得过重，应主动建议降到关键体检。

## 第三步：找基准

以**目标项目自己的规则**为基准，不要把别的项目的测试约定强加过来。逐项探测，找到什么用什么：

1. **成文测试契约**：`TESTING.md`、测试策略/计划、`CONTRIBUTING` 的测试章节、DoD 里的测试条款。摘出的硬性条款即为定级依据，违反者最低 P1。**边界：README 目录结构图、架构图等"声明性提及"（如画了 `__tests__/` 目录）不算契约条款**——不构成违约定级路径，但作为维度 11（声明与现实的差集）的对照源，差异记为文档失同步类发现。
2. **门禁与覆盖配置**：CI 配置、覆盖率阈值、排除项。**必须核对"声明的门禁"与"实际配置"是否一致**——这是缺口审计和覆盖率可信度的主要证据来源。
3. **flaky / skip 登记**：有登记的按已知项处理，不重复报告。
4. 都不存在时按通用标准审，报告里注明"该项目无成文测试契约"，**不得虚构项目规则**。

## 第四步：拆分与派发

### 分组规则：同一证据源必须同组

拆分的首要依据不是簇，是**证据源**。以下三组是硬绑定，不允许拆到两个子代理：

| 绑定组 | 维度 | 共享证据 |
|---|---|---|
| mock 组 | 2、5 | 同一批 mock 声明与断言写法 |
| 数据组 | 12、13、15 | 同一批 fixture、`testdata/`、`conftest.py` |
| 产物组 | 27、30、31、32、33 | 同一批 CI 配置、报告产物、覆盖率产物 |

理由：同一份文件被两个代理以不同维度读两遍，既浪费，又必然产出两条描述相近但级别可能不同的发现，汇总时靠人肉合并极易出错。

**默认分组（5 份子报告，34 维不重不漏）**：

| 子报告 | 所辖维度 | 数 |
|---|---|---|
| `01-测试有效性` | 1、2、3、4、5、6、7 | 7 |
| `02-覆盖与数据` | 8、9、10、11、12、13、15 | 7 |
| `03-设计与层级` | 14、16、17、18、19、20、21 | 7 |
| `04-非功能测试` | 22、23、24、25、26 | 5 |
| `05-工程与证据` | 27、28、29、30、31、32、33、34 | 8 |

（15 从 C 簇移入 02，使数据组三个维度同组；03 因此为 7 维。）

**例外——维度 9 跟随证据源（全量体检同样适用）**：9 的首选证据是覆盖率产物。全量分组下 9 在 02、产物组在 05——若 9 没有独立替代证据源（契约文档 ↔ 测试搜索差集，由摸底画像判断）而必须读覆盖率产物，则把 9 改归 05（02 变 6 维、05 变 9 维），避免同一份产物被两个代理双读；有替代证据源时 9 留在 02 照常评。拆分方案中注明 9 的归组依据。

### 规模与失败处理

规模参考：< 80 个测试文件用 1–3 个子代理；80–600 个用 4–6 个；> 600 个走交叉深审（核心链路全维度深审，其余快扫，快扫范围必须标注）。

**但子报告份数不随规模缩减。** 前面默认分组的 5 份是固定的，项目小时是**一个子代理连写 2–3 份**，而不是砍掉几组。理由：报告结构跨项目一致才能横向比较；砍组会让维度覆盖出现空洞。连写时每份报告仍须独立满足维度闭环与证据要求，不得因为合并书写而把两份并成一段。

**用户只选维度子集时（关键体检/定向评估/单模块深审），上面的默认分组表不适用**：按所选维度**重新分组**——先落证据源硬绑定（mock 组 2/5、数据组 12/13/15、产物组 27/30/31/32/33 中被选中的维度必须同组），其余按簇就近合并；子报告份数 = min(5, 实际分组数)。**出现辖 0 个已选维度的子报告（如关键体检下硬套"03-设计与层级"）是分组错误。**维度 9 跟随其证据源：被选中且要读覆盖率产物时与产物组同组，仅做契约↔测试差集时按簇就近。组名自拟用 `<序号>-<主题>` 格式（主题反映该组维度，如"01-有效性与覆盖"）。**多子项目仓库（如 1 后端 + N 前端）的摸底画像按子项目拆行统计**，不合并成一行。

派发要点：
- 指令**自包含**（模板见 `references/templates.md`）：子代理看不到本文件和主会话上下文，定级规则、只读禁令、所辖维度检查点、证据源提示都要写全。
- **同时运行不超过 6 个**，超出排队；子代理只读。
- 子代理失败：先重试一次；仍失败则自己降级亲审，并在报告里标注"该部分覆盖不完整"和缺失维度清单。不允许静默打折。
- **执行环境不支持子代理时**（AI 供应商限制、连续两次派发失败/被终止）：自动降级为**主会话亲审**——串行执行、同样的维度闭环与证据要求，报告头部标注"单会话执行"。降级要告知用户，但不中断流程；派发模板此时直接当亲审清单用（其中"子代理失败重试"等代理专属条目跳过），不需要改写。**关键体检 8 维的默认亲审顺序**：11（缺口基线）→ 27（门禁）→ 31（执行痕迹）→ 33（覆盖率）→ 1（断言）→ 2（mock）→ 4（flaky）→ 9（分支覆盖）——证据与基建类先行（其结论是后续维度的判定输入），质量类随后，9 最后（依赖 11/33 的结论）。其他维度组合按"结论依赖关系"类推。
- **拆分后的降级顺序**：`dimensions.md` 的"降级优先级"**只在单簇被完整派发时成立**。以下三种情况一律改为按**该维度失守后的后果严重度**排序（安全与数据完整性 > 主链路功能 > 工程质量 > 风格）：① 跨簇组合；② 同簇被拆到不同组（如 2、5 被分出去）；③ **两个及以上簇都完整派发**（如 05 组同时含完整的 F 与 G）。第 ③ 种尤其要注意：两个簇各有自己的原顺序，拼不出一个合法序列，硬拼会让主会话临时发挥。派发指令里必须写死具体顺序，不要留空；**单会话亲审同样先把顺序写进报告再动手**。（例：同组内同时有 23 安全与 25 兼容性，先亲审 23。）**组内仍定不出先后时，按结论依赖关系排：作为其他结论前提的维度先审**（如 27 门禁先于 33 覆盖率、31 执行痕迹先于 32 通过记录）。

## 第五步：回收质检

五项，缺一不可：

1. **维度闭环**：所辖维度是否都有结论；"不适用"的依据是否成立——这是最容易作弊的地方。**无依据的"不适用"不允许保留**：先退回重审，要求补依据（形态依据，或"零测试"时指向维度 11 的发现编号）；重审后仍无法判定的，归入"证据不可得"或按实际结论归入其余三类。不得用"未覆盖"这类不存在的类别绕过恒等式，也不得用无依据的"不适用"代替审查。
2. **证据齐全**：计入统计的发现是否都有 `文件:行号` + 片段。
3. **真实性抽验**：每份报告从 P0/P1 里随机抽 `min(5, 总数)` 条（不足 5 条全查），回文件核实行号与片段。抽到编造，该报告整体退回重审。
4. **纪律核查**：报告里是否出现"我运行了 xx 测试"，仓库是否多出 `coverage/`、`test-results/` 之类新产物（用 `git status --ignored` 查，普通 `git status` 看不到被 ignore 的产物目录）。有则记录，并作废依赖执行结果的那部分结论。**区分"本次新产生"与"审计前已存在"的历史产物**：后者只进摸底画像注记（它是审计对象的一部分，如过期的 surefire 报告恰恰是发现素材），不定级、不算违规；只有本次执行新产生的产物才触发作废。**不要删除这些产物**——删除同样是写操作，违反只读铁律；在报告里记录路径与生成时间，由用户自行清理。
5. **跨报告合并去重**：这一步不做，统计一定虚高。逐对比较子报告，以下四类几乎必然重复——数据与 fixture（12/13/15）、mock 与同构（2/5）、CI 与产物（27/30/31/32/33）、覆盖率产物（9/33——仅当 9 未按"跟随证据源"规则并入产物组时）。**同一对象被两份报告以不同维度评价时，合并为一条发现**：取最严重级别，证据行号合并，并在汇总里记"已合并 n 条重复"。合并后按去重结果统计，不按子报告相加。

## 第六步：出体检报告

主报告固定名 `00-测试体检报告.md`，子报告按维度组命名。主报告必须含六节，缺一节都算没做完。

### 1. 测试就绪度判定

**四选一，必须表态**：可发布 / 有条件可发布 / 不可发布 / **证据不足，无法判定**。

第四档不是退路，是诚实。触发规则分两种情形——**先看本次选了什么维度，再决定用哪条规则**，否则定向评估时分母为零，规则根本算不出来：

**通用口径：什么叫"失效"。** 情形 A/B 与混合模式中"失效 N 维"= 该维度结论为**"证据不可得"**（资产缺失与评审降级两种原因均计）；"不适用"不计入失效。

**情形 A：全量体检 / 关键体检**（所选维度包含核心 8 维中的 ≥ 3 个）。**边界缝**：用户自选维度恰含 3 个及以上核心维、但不是标准的关键体检 8 维组合时，仍按情形 A 判就绪度；00 报告"模式"栏写"自选体检（含核心维 <n> 个）"，未选的核心维照"未评核心维"规则列出。

- **0 个失效** → 按常规判档：**P0 存在，或关键链路验证不成立 → 不可发布**；**P0 为零、关键链路成立、P1 为零 → 可发布**（必须说明凭什么；**门禁项按配置层核实**——CI 配置存在、关键 job 无 continue-on-error/allow_failure 架空即算成立，平台运行历史拿不到时进待核实，依据栏声明"配置层成立，运行层未核实"，不得静默省略）；**P0 为零、关键链路成立、P1 存在 → 有条件可发布**（条件清单逐条列出各 P1 的修复与验证方式）；其余（如 P0 为零但门禁不生效）→ 有条件——注意"关键链路部分成立"已由下方定义直接封顶"有条件"，不再依赖"明显空档"这类模糊判断。**"关键链路验证成立"的操作化定义（审计模式下只看资产推断）**：鉴权、金钱/数据完整性、核心业务流程逐条检查，每条按**正向 + 反向**两向判定——
  - 鉴权：登录成功/失败（正向）+ 未登录访问需鉴权端点被拒（反向）；
  - 主业务流程：成功路径（正向）+ 主错误分支（反向）；
  - 金钱/数据完整性：正常扣减（正向）+ 失败回滚/幂等（反向）。
  三条路径正反向都有 → 成立；任一路径**反向缺失**（只有正向）→ **部分成立** → 就绪度**最高"有条件可发布"**，条件清单写"补齐反向测试"；任一路径**正向缺失**或断言无信息量（恒真/只断言不抛异常/零断言）→ 不成立 → 不可发布。**"部分覆盖 → 成立"不存在**。反向只认"访问/操作被拒"类测试：**水平/垂直越权类检查点（替换 ID、低权角色访问高权端点等）不算核心路径的反向**——它们归维度 23 处理：23 被选中就报 P1，未选中进未选维度清单（铁律 4），不因 23 未选而改变链路判档，也不会因 23 未选而误判不可发布。**"未登录访问需鉴权端点被拒"虽同属维度 23 矩阵的组成格，但它同时是鉴权链路的反向，两处引用同一证据不算重复报告**。**项目形态确无某类路径（如无金钱流）时，依据栏显式写"X 路径不适用于本项目形态"，不得省略该行**。
- **分母 = 所选维度中属于核心 8 维的那部分，不是全部 8 维。** 这 N 个里 **≥ 3 个失效**（典型：无 CI 历史、无报告产物、无覆盖率产物）→ 判"证据不足，无法判定"。
- 失效 **1–2 个** → 可以判定，但**最高只能到"有条件可发布"**，且必须在报告顶部列出失效的是哪几维、因此哪部分结论没有依据。
- 例：某次只选了 1、2、31 三个核心维（核心维计 3 个，属情形 A），其中 31 失效（无报告产物）→ 分母是 3、失效 1 个 → 最高"有条件"；若 1、2、31 全失效 → ≥3 → 证据不足。**不要用 4/9/33 举"失效"的例子**——它们有替代判定路径（见第一步证据可得性表），通常不直接判失效。同一份证据缺失常同时打掉多个维度，按实际失效个数计，不按证据条数计。
- 若所选核心维**不足 8 个**，判定必须附「**未评核心维**：<列出>；这些维度若失效或有问题，结论可能改变」。这与情形 B 的「结论仅覆盖 N 维」对称。典型漏评的是 9、11、27、31、33——恰好是最能翻盘的几维（覆盖率可信度、缺口审计、门禁、是否真执行过），不注明会让人以为核心维都看过了。

**情形 B：定向评估 / 单模块深审（且所选维度与核心 8 维交集 < 3 个）**——注意"单模块深审"不必然走 B：单模块但选了 ≥3 个核心维时按情形 A 判。判定只看交集数，不看模式名。

- 这种情况下"核心 8 维"分母为零，且拿两三个专项维度回答"能不能发布"本身就不成立。**默认不出就绪度判定**，改写为"不适用：本次为定向评估，仅就该 N 维给结论"。
- 用户明确要求就绪度时，改按**所选维度中失效占比 ≥ 1/3** 判"证据不足"；占比 < 1/3 时最高只能"有条件可发布"，且结论必须**限定为"就该 N 维而言"**——即使零失效、零 P0，也不给无限定的"可发布"，因为这几个维度本来就支撑不起整体结论。
- 无论哪种，都要在报告里说明"本次结论的适用范围是这 N 维，不是整个项目的发布结论"。

任何情况下不得把"没有证据"写成"可发布"。找不到反证不等于证明了安全。

**混合模式下，就绪度必须两账合看**——维度结论可以按回填规则维持原判（如维度 9 仍写"证据不可得（整体覆盖未知）"），但**整体就绪度必须把主动测试出的系统缺陷算进去**，规则独立于审计账：

- 06 报告有 **P0 系统缺陷**（越权可达、注入可利用、敏感泄露、弱默认管理员凭据等）→ 结论**封顶"不可发布"**（审计账更严时按更严者，见下行排序）。例外仅一个：用户明确接受风险，且条件清单逐项列出缓解措施与验证方式——**触发该例外时结论最高也只到"有条件可发布"**，不会回到"可发布"。
- 06 有 **P1 系统缺陷**（不限类型——"有 SLA 时性能未达标"这类非主链路 P1 同样封顶）→ 最高"有条件可发布"，条件清单必须包含对应修复项；**合账结论为"证据不足"时条件清单整节不填，系统缺陷修复项改写入 00 结论段（无论其槽位形态是"先补三个"还是"先补哪三样证据"）与 06 结论，不得丢失**。
- 06 **全部用例通过且无 P0/P1** → 可维持审计账的判定。
- **禁止只看审计账给"可发布"**：产品越权比测试资产问题严重得多。两账合看后，就绪度取两者中更严的结论。**"更严"的排序**：证据不足 > 不可发布 > 有条件可发布 > 可发布（"证据不足"是确定性维度，居首，且**不因 06 全部通过而改判**——它表达的是"无法确认"，不是"有问题"）；同时 06 有 P0 → 结论不得高于"不可发布"（除非触发上行的用户接受风险例外，且封顶"有条件"），06 有 P1 → 不得高于"有条件可发布"。
- **信号保底（呈现层，防"不知道"盖住"已经知道"）**：06 有 P0/P1 时，最终结论**必须同时显式写出该事实**——形如"**证据不足，无法判定；但存在 P0 系统缺陷（见 06 DEF-01），必须先修**"。排序维持不变，但报告不允许只写"无法判定"而不提 P0/P1——否则用户会去补 CI 记录而不是修越权。
- **审计账为定向评估（情形 B，无就绪度档位）时**：合账就绪度只按 06 缺陷封顶规则定——06 有 P0 → 不可发布；06 有 P1 → 最高有条件；06 无 P0/P1 → 维持"本次不适用（定向评估）"，但须附一句"另见 06 报告系统缺陷 <n> 条"。
- **P2/P3 不影响就绪度**（含 06 的"限流/锁定缺失"类安全 P2）：只进补测试建议表。审计账判"可发布"而 06 存在安全 P2 时，不降档，但须在条件清单或建议表中显式列出——口径要明确，不留"边界模糊"的解读空间。

判"不可发布"或"有条件"都要给依据；判"可发布"要说明凭什么（P0 为零、关键链路验证成立、门禁真实生效），不能只说"未发现严重问题"。

**选"有条件可发布"时，必须列出条件清单**，否则这一档等于和稀泥：

| # | 发布前必须满足 | 怎么算满足（可判定） | 归属 |
|---|---|---|---|
| 1 | 例：补齐支付失败分支的测试 | `tests/payment/refund.test.ts` 存在且覆盖 `status=failed` 分支 | 支付组 |

每项必须可判定、可指派。禁止写"建议加强测试""后续关注"这类无法验收的话。

### 2. 假绿清单

这是整份报告最有价值的一节。

**一条测试算假绿**，当且仅当：它存在，**且被当作通过**（有通过记录，或默认被计入覆盖率、被视为提供了保护），但满足以下任一条件——

**"通过记录"的口径**：工作区/仓库中存在的正式测试结果文件（surefire XML、junit 报告、CI 日志）即算"有通过记录"，**无论多旧**——过期产物证明的是"旧版本曾经绿过"（版本对应问题归维度 31），不豁免它所覆盖用例的假绿判定；采用此口径时在报告中声明。

- 断言不可能失败（永真式、被注释掉的断言、只断言"不抛异常"、断言写在 `try` 里被吞掉）
- 被测逻辑本身被 mock 掉（要验证的分支/计算被替换成了桩）
- 关键分支或错误路径从未进入
- 被 skip/ignore 且无理由，或只在特定环境、特定条件下才跑
- 断言的是实现细节（改实现就红，改行为不红）

**如果连"它是否通过"都无法确认**（无记录、无产物、无人知道跑没跑），**不要塞进假绿清单**，放第六节未决项。那种情况的问题不是"假绿"，是"没人知道它在不在"——属于维度 31/32 的范畴，混进假绿只会让这一节失去可信度。

每条写三样：**假装保护了什么 / 实际没保护什么 / 证据（文件:行号）**。按类型归组，同类合并成一条，**全量列出（含 P2/P3 级）**。这一节要让读者产生"原来这里一直没人管"的认知，而不是"测试有点弱"。

### 3. Top 问题

**只列 P0/P1，单条展开。** 与假绿清单的分工：假绿按类型列全量，Top 只挑最该现在处理的。同一问题已在假绿清单出现时，Top 里写"见假绿 #N"，不重复描述——两节各写一遍会让报告显得注水，也会让统计重复计数。

排序：先 P 级；同级按影响面广度；同广度按修复成本从低到高。

### 4. 补测试建议

每条缺口一行，回答"接下来补什么"，不写代码：

| 缺口 | 补在哪（层级 + 文件） | 断言什么 | 用什么数据 | 优先级 | 代价 |
|---|---|---|---|---|---|

"代价"用 小/中/大 三档（一个小用例 / 需造 fixture / 需补测试基建）。这张表就是可排期的清单，不必另开"测试债务台账"。

### 5. 覆盖说明

审了哪些维度、哪些没审（用户只选了子集时必须单列）、哪些是快扫、哪些因子代理失败而降级、**哪些因证据不可得而失效**。禁止让读者以为全审了。

### 6. 未决项

需要 CI 平台历史、覆盖率服务、issue 系统才能确认的，全部列在这里，标注"待核实"。**本应存在的本地产物（测试报告、执行日志）缺失时同样进未决项**，写明"本地产物缺失"——用例存在但从未见通过记录、又无法确认执行状态的归此类，不进假绿清单（它们可能从未被跑过，这本身是维度 31 的问题）。这些**既不当作"测试没执行"的结论，也不当作"已通过"的证据**；也**不计入假绿清单**。

## 铁律

1. **执行边界按模式。**
   - **审计模式**：绝对只读。不修改目标仓库任何文件；不运行任何测试命令、不带动覆盖率开关重跑、不安装依赖、不启动容器、不写快照。允许的手段只有：列目录、搜内容、读文本与报告产物、只读 git 命令（清单见 `references/discovery.md` 的「只读核验的边界」）。
   - **主动测试模式**：允许执行，但有四条硬边界——① **新写的测试代码只进暂存区**（报告目录 `active/`），移入仓库须经用户确认，且只新增文件、**不修改业务代码**；② **安全测试只做非破坏性探测**，且只针对用户自己的项目/本地环境，禁止对第三方系统、生产环境使用，禁止执行删除/改数据的攻击载荷；③ **压测默认轻载**（并发 ≤ 10、总量 ≤ 500），更大规模须经用户确认；④ 执行产生的临时文件/数据记录**清理状态**（清了什么、清没清），不留残余在业务仓库内。
2. **证据强制，形态按模式分账。**
   - **审计模式**：每条计入统计的发现必须有 `文件路径:行号` + 关键片段；靠猜的、靠外部系统才能确认的，一律进"未决项"，不计入统计。**否定性发现的合规格式**：应存在而查无的证据（如"CI 配置穷举命中 0""错误码在测试中命中 0"）用**搜索式 + 范围 + 命中数**呈现（例：`grep -r jacoco pom.xml → 0 命中`），可复现即合规，不要求行号。
   - **主动测试模式**：证据 = **可复现的请求-响应记录 + 环境声明**（用例 ID、方法/URL/头/体、状态码、响应摘要）——不要求文件行号，**禁止为凑格式硬造源码行号**；需要引用源码佐证根因时另附"推断根因（源码 `文件:行号`）"。
   - **混合模式**：两套证据各记各的账，不混算（审计发现用"<子报告号>-<序号>"如 02-03，维度归属写在发现条目里；主动测试缺陷用 DEF-<序号>；用例 ID 用 A-01 式组序号）；跨账引用写"对应审计发现 02-03 / 主动测试 DEF-01"。
3. **四级定级。** P0 阻断 / P1 严重 / P2 一般 / P3 建议。违反项目测试契约硬性条款最低 P1，同时触及安全或数据完整性升 P0，P0 封顶。测试资产类 P0 的锚点：真实生产凭据或未脱敏 PII 进了测试；安全路径（**定义：鉴权、会话管理、密码处理、令牌签发与解析、加密、敏感数据访问的代码路径**——工具类如密码哈希/令牌解析的测试也算，从宽认定）的测试把被测逻辑 mock 掉、删掉断言或**从未写过断言**（三者等效，git 历史可证"从未写过"时同样成立）形成假绿；门禁被系统性绕过且鉴权/金钱/数据完整性路径无有效验证（**"绕过"需要门禁存在的证据**——存在 CI/门禁配置但被 continue-on-error、allow_failure 等架空才算；**从未建过门禁不算"绕过"**，按 P1"门禁不存在"处理）；**测试产物与当前代码版本不对应，却被作为验证通过的证据**（评的是"对应关系不成立"这个客观事实，不评动机）。**"被作为证据"的取证方法（三选一即成立）**：① 产物在 git 中已被提交；② CI 门禁配置引用它；③ 文档/README/提交信息引用其数字。**产物仅位于标准报告路径（`surefire-reports/`、`coverage/` 等）但未提交、无人引用 → 不算成立**（工具自动输出常无人查看），此时**降 P1**，并注明"是否被采信无法核实"。
4. **范围诚实。** 选了 N 个维度就报 N 个维度的结论，未选维度必须在报告里单列，不得暗示已全审。恒等式：**所选维度 = 有发现 + 未发现 + 不适用 + 证据不可得**。第四项含两种原因——**资产缺失失效**（项目缺 CI 历史/报告产物/覆盖率产物）与**评审降级未审**（子代理失败且未亲审），报告中须分列，计数不变。
   **恒等式只适用于审计账。** 主动测试的产物是"用例 × 通过/失败/阻塞"，用**用例统计**记账（通过 X · 失败 Y · 阻塞 Z），不套用维度恒等式；混合模式两账并行。
   **四类互斥，一个维度只归一类**，判定优先级：**有发现 > 不适用 > 证据不可得 > 未发现**。所以"查出 2 条问题、但覆盖率产物缺失导致整体无法确认"归**有发现**，在说明列注明"缺覆盖率产物，整体覆盖情况无法确认"——不能因为有缺口就改判"证据不可得"，那会把已经查实的问题藏起来。同理，形态上不适用（如纯 CLI 无可访问性面）优先于证据缺失，因为根本不该去查。
5. **不适用须给依据。** 「不适用」只有两种合法依据：① **项目形态不适用**（如纯后端服务无可访问性面）；② **无评测对象**（该模块零测试，且已由维度 11 的发现佐证，须指向具体发现编号）。两种都必须写明依据，且不计入"已覆盖"；无依据的"不适用"视为未覆盖。
6. **输出目录纪律。** 默认**不进被审计仓库**；用户指定则从其指定。"工作区"的锚点：**有会话工作区、且工作区不是被审项目根（或其内部）时**，用工作区内路径（如 `<工作区>/test-report-<YYYYMMDD>/`）；**其余情况（代理/离线形态、无会话工作区、或会话工作区就是被审项目）**一律用**被审项目根的父目录**下的 `test-report-<YYYYMMDD>/`（与项目并列，不进仓库）——不许落到执行者无法预期的随机位置。全部候选位置均不可写时（离线无用户可问），如实停止并说明原因，**不得改投仓库内**。写入受限时向用户报告并请其另选位置，**不得改投到被审计仓库内**（会污染仓库，也让"未改动仓库"的承诺失效）。
7. **不虚报。** 不为凑数降级或夸大，不把快扫包装成全量，零发现就写"未发现"，证据不足就写"无法判定"。

## 完成标准

> **模式分账**：下列前 6 条只约束**审计账（含混合模式的审计部分）**；**纯主动测试模式**不产 00，跳过前 6 条，按末两条的执行账与"纯主动测试"条对账。

- `00-测试体检报告.md` 存在，六节齐全，子报告与拆分方案一一对应。
- 所选维度全部有结论，恒等式成立；未选、快扫、证据失效的维度均已单列。
- 若判"证据不足"，已列出失效维度；若判"有条件可发布"，条件清单的每项都可判定、可指派；**定向评估下若按情形 B 未出就绪度，已写明原因与"结论仅覆盖这 N 维"的适用范围**。
- 每个"证据不可得"的维度，在未决项里至少有一条对应记录（未决项可以多于失效维度，但不能有失效维度却无对应未决项）。
- 每条计入统计的发现证据可定位；P0/P1 抽验通过；跨报告重复已合并并记录条数。
- **审计/混合模式的审计账**：确认审计阶段未执行测试、未改动目标仓库（含 `git status --ignored` 检查产物目录）。
- **主动测试/混合模式的执行账**：执行的命令、产生的产物（暂存区路径）、对目标环境的临时写入（如会话键注入）与**清理状态**均已记录；执行前后 `git status` 对比无仓库污染；被测服务版本已记录（见 active-testing.md 执行环境节——**被测版本 ≠ git HEAD 时本身记为发现**）。
- **纯主动测试模式**：`06-主动测试报告.md` 存在且总览统计闭合（通过 X + 失败 Y + 阻塞 Z = 用例总数），阻塞逐条有原因；缺陷编号 DEF 连续唯一；执行环境各字段已填（缺项写"未记录"）；矩阵中每个用例都有结果。
- **混合模式两账不混算**：体检报告与 06 报告各自成立，交叉引用按铁律 2 的编号规则。
- **混合模式的回填规则**：主动测试的实测结果只作为"**已验证某点**"的补充记录——回填进体检报告覆盖说明的"补充证据"栏（格式："已验证：分支 X 的单测通过 / 接口 Y 的越权被拦截，见 06 A-05"），**不改变维度结论的定性**。维度 9 曾判"证据不可得"的，仍写"证据不可得（整体覆盖未知）"，另起一行补充实测点；只测一个点不足以改判"未发现"，也不足以推翻原结论。
- 最终回复按模式选模板（收尾回复有五个变体：正常版、证据不足版、定向评估版——审计用；混合模式变体、纯主动测试模式变体——见 `templates.md`，按模式选）：情形 A 给就绪度判定；**情形 B 给"本次不适用（定向评估），结论仅覆盖 N 维"，不得塞进"证据不足"那个模板**。两者都要给各级别数量、最该先补的 3 件事（带文件:行号；证据不足变体此槽位按"已查实问题优先"填——有查实 P0/P1 按 Top 取前 3，Top 为空才改为"先补哪三样证据"，均不受行号要求约束）、报告路径，并问一句是否要把补测试建议排进迭代（需另行确认，本次不做）。**用户预授权/离线代办形态下**（如由子代理全程执行、用户已预先回答全部确认问题），该确认问句改为陈述（"如需排期请告知"），不阻塞；报告须注明执行形态（单会话亲审 / 多代理 / 离线代办）。
