# 维度选择与范围界定

> 用户说"你按风险定"或"不知道选哪些"时，用本文件挑维度。挑完要在报告里说明挑了哪些、为什么，不能默默替用户决定。
> 完整检查点见 `dimensions.md`，证据源见 `discovery.md`。

## 一、34 维的三档分组

**核心 8 维**（默认"关键体检"，判断可信度的最小集）：1 断言强度、2 mock 边界、4 flaky 治理、9 分支/异常路径、11 缺口审计、27 CI 集成、31 是否真执行过、33 覆盖率可信度。

**标准 15 维**（全量体检时该查，影响"好不好用、稳不稳"）：3 独立可重复、5 与实现同构、6 失败诊断、7 测试代码质量、8 需求映射、10 契约覆盖、12 数据代表性、14 等价类边界、15 fixture 隔离、17 命名组织、18 层级匹配、19 缺失层级、30 报告可读性、32 通过记录、34 缺陷回归闭环。

**专项 11 维**（有对应形态或资产才查）：13 数据合规、16 时间/随机可控、20 回归集、21 冒烟集、22 性能、23 安全、24 可靠性、25 兼容性、26 可访问性、28 并行分片、29 环境依赖。

三档相加 = 34。用户自选时按编号勾，不必按档。

## 二、项目特征 → 该加查哪些维度

> 先探测特征（左二列），命中就把对应维度加进本次范围。这是"按风险定"的实际做法。

| 项目特征 | 探测线索 | 必加维度 | 为什么 |
|---|---|---|---|
| 涉及金额、计费、结算 | `payment` `billing` `amount` `price` `refund`、账单/流水表 | 23、9、12、24 | 金额算错一次就是事故，且往往只在边界与重复请求上暴露 |
| 有鉴权、多租户、权限体系 | `auth` `permission` `role` `tenant_id` `acl` | 23、10、13 | 越权是最高频高危；租户隔离失效靠 happy path 测试发现不了 |
| 有 Web/移动/桌面前端 | `react` `vue` `next` `app/` `android/` `ios/`、组件目录 | 26、25 | 可访问性与浏览器矩阵是用户可见面，且必须有依据才能判不适用 |
| 有异步任务、队列、定时调度 | `mq` `kafka` `celery` `cron` `scheduler` `job` | 24、4、16 | 时序与并发是 flaky 主产地，也是最难补测的地方 |
| 依赖外部服务/第三方 API | http client、SDK 依赖、`*_client` 目录 | 2、29、24 | 全量 mock 会让测试失去信息量，且 mock 会与真实契约漂移 |
| 有数据库、迁移、复杂 schema | `migrations/` `schema` ORM 模型 | 15、12、13 | 测试数据污染与残留是"本地过、CI 挂"的常见根因 |
| 刚接手 / 没有 CI | 无 `.github/workflows` 或 CI 配置里没有 test job | 27、31、32、30 | 先解决"有没有在跑"，再谈测试质量；顺序反了会白审 |
| 覆盖率很高但线上问题多 | 覆盖率报告 + 缺陷/issue 记录 | 33、1、5、2 | 典型假绿画像，优先验证百分比的真假 |
| 有性能 SLA / 高并发场景 | SLA 文档、压测脚本、QPS 目标 | 22、24 | 容量与降级路径必须在上线前有数，不能靠"应该没问题" |
| 处理 PII、医疗、金融数据 | `email` `phone` `id_card` `address`、合规文档 | 13、12、23 | 合规红线，测试里出现真实数据即是 P0 |
| 微服务 / RPC / 对外 API | `proto` `grpc` `openapi` `swagger`、契约文件 | 10、29 | 契约漂移只能靠契约测试兜住，单测覆盖不到 |
| CI 单次执行很久（>30 分钟） | workflow `timeout`、无分片配置、串行 job | 28、27 | 慢会直接导致"本地跑一半就合了"，门禁形同虚设 |
| 仓库里有大量 skip/ignore | 搜 `skip` `@Disabled` `#[ignore]` `xit` | 31、4 | 长期 skip 且无理由的用例是死测试，最容易被当成"有覆盖" |
| 多人长期协作、测试风格混乱 | 多作者提交、`CONTRIBUTING` 测试章节 | 17、7、34 | 一致性问题会指数级放大维护成本 |

命中多个特征时取并集，但**总维度数超过 20 就建议直接上全量体检**——挑挑拣拣的沟通成本已经超过省下的时间。**前提是用户没有明确限定维度**：用户已经说了"只看 1、2、4"时，就按他选的做，不要再按特征表往上加，那会违背他的意图。

## 三、用户口语 → 维度映射

用户往往说不出维度名。把他的话翻译过来：

| 用户这么说 | 实际想知道 | 建议维度 |
|---|---|---|
| "覆盖率 80% 靠不靠谱" | 这个数字能不能当证据 | 33、9、1 |
| "测试老是挂，重跑又好了" | 稳不稳定 | 4、3、16、28 |
| "改完不敢合，怕漏" | 回归保护够不够 | 20、21、27、32 |
| "写了一大堆测试但好像没用" | 有没有实际保护力 | 1、2、5、8 |
| "上线前帮我把把关" | 能不能发 | 全量 34 维 |
| "不知道从哪开始" | 先看最要紧的 | 核心 8 维 |
| "这个模块没人敢动" | 这块的测试是不是摆设 | 该模块核心 8 维 + 5 |
| "新人接手的项目" | 整体健康度 | 全量或核心 8 维 + 30、34 |

## 四、范围界定方法

四种范围，各自的定位方式（全部只读）：

**整个项目**：以仓库根为界，默认排除 `node_modules`、`vendor`、`dist`、`build`、第三方测试、E2E 录屏与截图本体。排除项要随方案告知用户。

**某个模块/目录**：优先按目录定位；目录组织与源码不同构时，用三种方式反查——
1. 路径匹配：测试文件路径含模块名（`test/payment/`、`payment.test.ts`、`test_payment.py`）
2. 命名匹配：测试名/describe 块含模块名或其主要类名
3. 引用反查：搜测试文件里 import/require 了该模块路径的地方

三种方式取并集，并说明"该模块的测试分布在 N 个目录"。若某模块**一个测试文件都找不到**，这本身就是最重要的发现，不要因为"没东西可审"而跳过——直接进缺口审计与假绿清单。

**最近改动的部分**：`git log --oneline -20` → `git diff --name-only <base>..HEAD` 拿变更文件 → 按三条路径反查到测试（路径匹配 / 命名匹配 / 引用反查），完整方法与结果解读见 `discovery.md` 的「变更集 → 测试文件的映射」。这个范围最适合回答"这次改动有没有测试兜着"，也最适合放进 PR 前的检查。报告中须写明 base 与 HEAD，否则读者无法复现审的是哪一批改动。

**某个测试套件/层级**：按目录（`tests/integration/`）或标记（`@Tag`、`pytest.mark`、`*.e2e.ts`）定位。注意跨套件维度（18 层级匹配、19 缺失层级、28 并行分片）只能评本套件内的表现，全局结论要回到整项目看。
