# 主动测试模式手册

> 供主会话在主动测试/混合模式下使用。核心思想：**测试设计先行、执行留痕、失败与通过同等记录**。
> 安全红线贯穿全文：只测用户自己的项目与本地环境，非破坏性，禁止对第三方/生产系统使用任何本手册的攻击类手段。

## 〇、两套定级不混用

本手册的缺陷定级对象是**系统本身**（产品缺陷），与 SKILL 铁律 3 的"测试资产定级"（评审对象的缺陷）是两套体系，同一次混合模式作业中并行使用、各自编号：

| 级别 | 系统缺陷锚点（主动测试用） |
|---|---|
| **P0** | 越权可达（水平/垂直）、注入可利用、敏感信息实际泄露（凭据/他人数据可取）、金额或数据完整性错误、弱默认管理员凭据 |
| **P1** | 主链路功能错误、契约不符（状态码/错误码/响应结构与文档不符且影响调用方）、并发下丢失更新/超卖/重复扣减、有 SLA 时性能未达标 |
| **P2** | 边界与错误处理瑕疵、非关键路径错误码不符、无 SLA 时性能明显异常、限流/锁定机制缺失（暂无可利用后果） |
| **P3** | 表现层不一致、无实际利用路径的信息暴露、文档与实现不一致（无功能影响） |

编号规则（三套互斥）：**主动测试缺陷用 `DEF-<序号>`**（DEF-01、DEF-02…，全局唯一）；**矩阵用例 ID 用 `<组>-<序号>`**（A-01=黑盒组第 1 例、S-03=安全组第 3 例——组字母表：A 黑盒、W 白盒、P 性能、S 安全、C 并发；注意性能组用例 ID 形如 P-01，首字母 P 是组字母不是 P0/P1 级别，勿混淆）；**审计发现用 `维度 N` + 发现编号 `<子报告号>-<序号>`**（如 02-03，全局唯一，见 templates.md 子报告模板）。同一问题两账都出现时，缺陷条目里写"对应审计发现 02-03"。

## 〇-2、测试类型怎么选（项目特征 → 推荐表）

用户不点名时按此表推 **2–3 类**贴给用户确认，不要默认四类全做：

| 项目特征 | 推荐类型 | 理由 |
|---|---|---|
| 有 API 文档 / OpenAPI | 黑盒 | 有规格可对拍，文档-实现不一致本身就是发现 |
| 有纯函数 / 校验器 / 解析器模块 | 白盒 | 独立跑得起来，ROI 最高 |
| 有 SLA / QPS 目标 | 性能 | 无 SLA 时基线意义有限 |
| 有鉴权 / 多租户 / 金额 | 安全 + 并发正确性 | 越权与超卖是最高频高危 |
| 有队列 / 定时任务 | 并发正确性 + 故障注入 | 时序 bug 单请求测不出来 |

## 一、用例设计方法（四类测试共用）

设计用例矩阵时按三种技术取材，每个用例必须可追溯到设计依据（不能凭感觉堆用例）：

| 技术 | 用法 | 例 |
|---|---|---|
| **等价类划分** | 每个输入参数划有效/无效等价类，每类至少一个代表用例 | 学号：8 位数字（有效）/ 空串、含字母、超长、不存在但格式合法（无效） |
| **边界值分析** | 取边界及邻域：min、min+1、max、max+1、空、null | 分页 pageSize：0、1、最大值、最大值+1；密码长度：规则下限-1/下限/上限/上限+1 |
| **错误推测** | 凭经验列出易错场景 | 重复提交、并发同键、Token 刚好过期那一刻、Content-Type 错误、UTF-8 特殊字符 |

**矩阵格式**（执行前贴给用户确认）：

```markdown
| ID | 类型 | 前置 | 输入/操作 | 期望 | 设计依据 |
|---|---|---|---|---|---|
| A-01 | 黑盒-鉴权 | 无 | POST /login {正确账号, 错误密码} | 401/错误码，不泄露账号存在性 | 错误推测 |
| A-02 | 黑盒-边界 | 无 | pageSize=0 | 400/默认值，非 500 | 边界值 |
```

粒度参考：核心接口一组 8–15 例（正常 2–3、无效等价类 4–6、边界 2–4、鉴权/权限 2–4）；整轮测试 30–60 例通常够暴露问题，超过就按风险砍。

## 二、黑盒接口测试

1. **规格来源**：API 文档 > 接口代码 > 前端调用代码。文档与实现不一致本身就是发现（记入缺陷，注明以哪边为准待确认）。
2. **先探路况**：第一个真实请求永远用最无害的端点（如公共查询/健康检查），确认 host、context-path、Content-Type、统一响应结构，再开打。
3. **每个用例记录**：请求方法/URL/头/体 + 响应状态码/体摘要（长体截断，保留关键字段）。失败用例必须完整可复现。
4. **断言什么**：状态码、业务码（code 字段）、关键响应字段存在性与类型、**错误分支的错误码是否符合文档**。"返回 200 但业务码错误"是常见缺陷形态。
5. **幂等与重复**：对写操作（若用户允许）做一次重复提交验证；**禁止**在未确认的情况下执行删除/更新类写操作——先问。

## 三、白盒单元测试

1. **选点**：优先纯函数（工具类、校验器、解析器）；其次有依赖但可注入 fake 的 service。**从审计报告的"零覆盖高危路径"清单里选**——这是主动测试对审计最大的增值。
2. **写法**：与项目同栈同框架（JUnit5/vitest/pytest…），命名 `MethodName_条件_期望`，一个用例一个断言焦点。
3. **运行（可行性与语言强相关，如实选择路径）**：
   - **Python / Node**：从暂存区 import 目标模块独立进程跑，通常可行。
   - **JVM（Java/Kotlin）**：`javac -cp` 手拼依赖链基本不可行（版本对齐是坑）。现实路径只有两条：① 测试文件入库走 `mvn test`/`gradle test`（**需用户确认**）；② 独立临时 Maven 工程 + 依赖项目 pom（成本高，需用户确认）。两条都不接受时，白盒降级为"**用例已设计未执行**"+ 把分支行为转化为黑盒用例（通过 API 触达该分支），不假装跑过。
   - **.NET / Rust / Go**：同 JVM，必须走 `dotnet test` / `cargo test` / `go test`，独立跑基本不可行，处理方式同上。
4. **白盒用例同样要矩阵**：哪个方法、哪个分支、为什么这个分支值得测（关联审计发现的哪条缺口）。

## 四、性能测试

1. **选点**：只读端点优先（查询/列表/首页）；写操作压测必须用户单独确认。
2. **默认轻载**：并发 ≤ 10、总请求 ≤ 500、持续时间 ≤ 60s。开发机上压垮它没有任何价值——目标**不是极限**，是**基线**。
3. **产出指标**：总请求数、成功/失败数、RPS、P50/P95/P99 延迟、错误率。两轮对比（如冷/热）优于单轮数字。
4. **工具从简**：Python `asyncio`/`concurrent.futures` + 标准库、Node 脚本、`ab`/`wrk` 有哪个用哪个，**不为压测安装重型依赖**。
5. **环境声明**：压测数字离开环境毫无意义——报告必须写明"本机开发环境、规格 X、数据库同机"，禁止把数字当成生产容量结论。

## 五、并发正确性测试（与性能压测是两回事）

性能压测关注吞吐与延迟（用不同数据、不查正确性）；**并发正确性**关注"单请求都对、并发时出错"。真实项目最贵的 bug 在这里。五类必测场景：

| 场景 | 打法 | 判定 |
|---|---|---|
| **幂等** | 同一请求原样重发 N 次（用专门造的数据） | 副作用只发生一次 |
| **超卖/超扣** | 并发扣减同一资源（库存/余额/额度） | 最终值 = 初始值 - 成功请求数 |
| **丢失更新** | 两个会话同时读-改-写同一行 | 最后状态符合声明策略（非静默覆盖） |
| **分布式锁** | 并发抢同一把锁 | 互斥生效；持锁方超时后行为符合设计 |
| **重复提交** | 同一表单/订单号并发提交两次 | 不产生两条记录；或幂等键生效 |

约束：全部使用**专门造的测试数据**，不碰已有业务数据；写操作类场景须经用户确认；无写权限时退化为"会话类并发"（如同一账号并发登录 N 次，验证会话覆盖/互踢语义符合设计）。**会话类不需要写权限，但仍受第六节安全硬化规则第 2 条约束**——并发登录恰恰最容易触发锁定/风控：执行前确认目标账号的风控/锁定策略；**对真实管理员账号不打**，用专门测试账号或经用户确认。

**故障注入（可靠性子项，按项目特征选做）**：kill 服务、断网、注入延迟、依赖（DB/Redis）不可用，验证降级/重试/熔断路径真的工作。比压测更能暴露可用性问题，但影响运行环境——只在用户确认的本地环境做。

## 六、安全测试（非破坏性）

**红线（违反任何一条立即停止）**：只测用户自己的项目；禁止对生产环境；禁止删除/篡改数据的载荷；注入探测只发"能引发错误即可被识别"的 payload，不做脱库、不大量拉取；发现可利用漏洞**只记录证据，不深入利用，不扩散**。

**真实项目硬化规则（四条，都来自实际会出事的场景）**：

1. **"本地"不等于安全**：dev 环境连生产库或生产克隆很常见。执行写操作类用例前确认目标数据库不是生产；**不确定时，安全测试降级为只读探测**（只打无副作用端点），写操作类全部转"未执行 + 原因"。
2. **鉴权矩阵会触发锁定/风控**：连续错误密码可能锁死管理员账号或触发告警。执行前确认锁定策略与风控阈值；必要时用**专门测试账号**（经用户确认创建），不对真实管理员账号暴力打。
3. **注入载荷会留脏数据**：`'`、`<script>` 若被持久化会污染后续测试与展示。用带明显测试标记的专门数据（如 `tst_` 前缀），测后确认未持久化；持久化了就记录并清理（仅限自己刚写入的）。
4. **压测不触达付费依赖**：压测路径若链到短信/支付/第三方 OCR，先确认沙箱与额度，否则换纯本地端点。

按四层推进，每层发现即记录（编号、请求、响应、影响）：

1. **鉴权矩阵**（最重要，通常是黑盒安全测试的主产出）：

   | Token 状态 | 访问需登录端点 | 访问管理员端点 | 访问低权端点（如普通用户） |
   |---|---|---|---|
   | 无 Token | 期望 401 | 期望 401 | 期望 401 |
   | 伪造/畸形 Token | 期望 401 | 期望 401 | 期望 401 |
   | 过期/篡改签名 Token | 期望 401 | 期望 401 | 期望 401 |
   | 合法低权 Token | 正常放行（200）——放行才是对的 | 期望 403（垂直越权被拦） | **分两格测**：访问自己的资源 → 期望 200；访问他人资源（替换 ID）→ 期望 403/404（水平越权被拦）。**合法 Token 拿到自己资源返回 200 不是缺陷，别误报** |

   **每个格子都要真打一遍**。"低权 Token 能不能调管理员接口"（垂直越权）、"能不能看别人的单据"（水平越权，替换路径/参数里的 ID）是最高频的真实漏洞。

2. **输入类探测**：注入类 payload 只验证"被拒绝/被转义/报参数错误"（如 `'`、`1=1`、`<script>`、超长串、格式串 `%n`），看错误码与响应是否异常（500 + 堆栈 = 发现）。
3. **信息暴露**：错误响应是否带堆栈/SQL/内部路径；响应头是否泄露服务器版本；统一响应是否把内部字段（密码哈希、secret）序列化出去。**源码审计发现的硬编码凭据**（application.yml 里的密码/secret）在此升级为"配合接口可利用性"评估。
4. **业务逻辑**：验证码是否真的校验（不填/错的也放行?）、找回密码流程能否跳步骤、限流是否存在（同错误密码连打 20 次看是否锁定）。

## 七、执行环境声明（必填，防"测错对象"）

| 字段 | 记什么 |
|---|---|
| 被测服务版本 | 启动方式（本 skill 启动 / 用户已运行）、**对应哪个代码版本**（git HEAD？工作区含未提交改动？一周前启动的 jar？）。定级：无法确认被测版本对应哪次提交 → **P1**（可能测的不是要发的代码）；确认与被审版本不一致且差异涉及被测路径 → **P1**；仅编译缓存导致的时间戳差异、代码一致 → **P3** |
| 部署形态 | jar 直跑 / 容器 / 集群；关键 JVM 参数 |
| 机器规格 | CPU / 内存 |
| 数据库 | 类型、版本、与被测服务是否同机、**是否可能是生产或生产克隆——不确定时安全测试降级为只读探测** |
| 依赖服务 | Redis/MQ/第三方；注明哪些是**付费依赖**（短信、支付、OCR）——压测与安全测试前确认不触达。**触达生产付费依赖的测试执行本身记 P1**（成本风险 + 可能影响真实业务） |
| 冷/热状态 | 是否刚启动、连接池/缓存是否预热 |

## 八、执行纪律

1. **暂存区结构**：

   ```
   <报告目录>/active/
   ├── matrix.md          # 用例矩阵（设计稿 + 执行结果列）
   ├── scripts/           # 执行脚本（黑盒驱动、压测脚本）
   ├── evidence/          # 原始证据（请求响应记录、压测原始输出）
   └── unittest/          # 白盒用例（待用户确认入库）
   ```

2. **失败优先**：失败的用例在报告里排在通过的前面；每个失败标注疑似根因（基于响应行为与源码阅读的推断，标注"推断"）。
3. **不污染仓库**：执行前后各跑一次 `git status`，确认测试没有在业务仓库留下文件（上传的文件、日志、临时产物）；留了就记录路径并清理（清理目标仅限**测试自己产生的**文件）。
4. **环境如实**：起不起得来、数据库连没连上、用了哪份配置，全部写进报告的"执行环境"节。环境不完整导致某类用例没跑成，写"未执行 + 原因"，不算通过也不算失败。
5. **报告**：`06-主动测试报告.md`（模板见 templates.md）——执行环境、用例矩阵执行结果、缺陷清单（按 P 级）、性能基线、安全发现、未执行清单与原因。
