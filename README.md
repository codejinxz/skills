# Skills

## 为什么需要这套 Skills？

AI 编码会话最大的风险不是「不会写代码」，而是「假装写了代码」——永真断言、被注释掉的断言、mock 掉被测逻辑、用 `skip` 掩盖 flaky、门禁被 `|| true` 架空。这类问题不会让构建变红，只会让「全绿」失去意义，而通用 Prompt 无法系统性地堵住它们。

本仓库把资深评审员与测试工程师的**判断纪律**，固化为 AI 必须遵守的执行契约：

- **只审不改** —— 审查阶段禁止修改目标仓库的任何文件，杜绝「边修边自批」；修复是另一个任务，不能并进审查流程。
- **四态结论** —— 每个检查项必须落到四种状态之一：有发现 / 未发现 / 不适用（附依据）/ 证据不可得（写明缺什么才能确认）。不接受「大概没问题」。
- **证据强制** —— 计入统计的结论必须可追溯到 `文件:行号` 加代码片段，或一条可重跑的命令；无锚陈述一律进「待核实」区，不计入统计。

## 这是什么

面向 AI 编码会话的**技能包（Skill）集合**。每个技能是一份结构化的操作规范：定义触发条件、工作流程、产出格式与边界，让 AI 在特定任务上从「凭感觉发挥」转为「按流程执行」。

当前收录三个技能，分别覆盖**代码评审**、**测试工程**与**提示词工程**。

## 技能一览

| 技能 | 定位 | 典型触发 | 产出物 |
|---|---|---|---|
| [`code-reviewer`](code-reviewer/SKILL.md) | 多代理全维度代码评审编排器，32 维度系统评审，只审不改 | 「评审代码」「上线前审查」「全量代码体检」 | `00-评审汇总.md`（32 维映射表、恒等式校验、Top 10、整改路线）+ 按拆分单元的子报告，P0–P3 分级且每条附 `文件:行号` |
| [`test-engineer`](test-engineer/SKILL.md) | 测试工程师双模式：审计现有测试是否可信 / 主动设计并执行测试 | 「测试质量怎么样」「帮我测测这些接口」「压测一下」 | 审计：体检报告 + 假绿清单 + 就绪度判定；主动测试：用例矩阵 + 执行证据 + 缺陷清单 + RPS/P95 基线 |
| [`write-prompt`](write-prompt/SKILL.md) | Prompt 工程师工作流，补齐目标、上下文、约束、完成标准四要素 | 「帮我写个 prompt」「把需求变成给 AI 的指令」 | 结构化、可审查的 Prompt（Goal / Context / Constraints / Done when） |

### code-reviewer

以「主会话当评审负责人 + 多个只读子代理并行评审」的架构，对目标代码做 32 维度、不重不漏、证据强制的系统评审。主会话负责拆分方案、子报告质检与维度覆盖，不逐行评审全部代码。**流程内不存在修复环节**，产出为按严重级别分级的多份报告与一份全局汇总。

```text
主会话（评审负责人：对拆分方案与质检负责，不逐行读全库）
├─ ① 摸底       契约要点 · 模块规模 · 高风险区 · 已知缺口登记
├─ ② 拆分方案   维度聚簇 / 按模块拆 / 交叉深审（<200 / 200–2000 / >2000 文件）
├─ ③ 并发派发   只读子代理，同时运行 ≤ 6，超出排队
│   ├─ 子代理 A → 01-xxx.md 子报告
│   ├─ 子代理 B → 02-xxx.md 子报告
│   └─ 超时或残缺 → 重试一次 → 主会话降级亲审，标注覆盖不完整
├─ ④ 回收质检   每份 P0/P1 抽 min(5, n) 条回源码核实行号；不符则整份退回重审
└─ ⑤ 全局汇总   维度→子报告映射 + 32 维恒等式校验 + Top 10 + 整改路线
```

全程只读：完成标准包含用 `git status` 确认目标仓库没有任何改动。

- `references/dimensions.md` — 32 个评审维度的定义与判定标准
- `references/templates.md` — 子报告与汇总报告的固定骨架

### test-engineer

两种被需要的方式：**审计**（判断现有测试值不值得信任，产出测试体检报告、假绿清单、就绪度判定，34 维）与**主动测试**（黑盒接口测试、白盒单元测试、性能压测、安全探测，自己出用例并实际执行）。两模式可混合：先审计摸底，再对缺口做主动验证。

- `references/discovery.md` — 项目与测试资产发现
- `references/dimensions.md` — 34 个审计维度
- `references/selection.md` — 测试策略选取
- `references/active-testing.md` — 主动测试执行纪律
- `references/antipatterns.md` — 假绿与无效测试的典型反模式
- `references/templates.md` — 报告模板

### write-prompt

通过多轮追问收集四要素（Goal / Context / Constraints / Done when），把模糊需求转化为结构化、可执行、可审查的 Prompt。原则是**先盘点已知信息再追问**，过度追问是用户放弃这类工作流的第一原因。

## 目录结构

```
skills/
├─ code-reviewer/
│  ├─ SKILL.md
│  └─ references/
├─ test-engineer/
│  ├─ SKILL.md
│  └─ references/
└─ write-prompt/
   └─ SKILL.md
```

每个技能目录以 `SKILL.md` 为入口（YAML frontmatter 提供 `name` 与 `description` 供检索与触发），`references/` 存放按需加载的细则，避免主文件膨胀。

## 安装

技能以目录形式分发，放进所用 Agent 客户端的技能目录即可被识别：

```bash
git clone https://github.com/codejinxz/skills.git
cp -r skills/code-reviewer skills/test-engineer skills/write-prompt ~/.agents/skills/
```

部分客户端同时支持项目级安装：把技能目录放到项目内的 `.agents/skills/`，仅对当前项目生效。具体路径以所使用客户端的文档为准。

## 设计约定

- **单一入口**：`SKILL.md` 只写流程与判定，细则下沉到 `references/`，按需读取。
- **边界显式**：每个技能都写明「不做什么」。评审不改代码，审计不跑测试，测试不碰业务代码。
- **降档可见**：子代理失败、覆盖从深审降为快扫，都必须写进报告；降档允许，静默打折不允许。
- **产出落盘**：报告写入指定目录而非仅停留在对话中。
